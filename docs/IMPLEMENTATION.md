# 实施计划

状态基准：2026-11-13。以下“已验证”只表示本地原型证据；未部署 Cloudflare。

## 已有基础

- 固定 Sub-Store Workers 适配分支 2.44.2 和依赖锁文件。
- 999 节点真实解析/处理/输出链路在本地 workerd + SQLite DO 运行。
- QuickJS HTTP 桥接、中断预算、显式脚本错误的实验实现。
- SQLite 配置跨 workerd 重启恢复；并发 patch 保留两个字段。
- 999 次模拟 HTTP 查询按 40 条/批处理，Alarm 自动推进，缓存与中途重启恢复已验证。

## 阶段 1：建立可维护的 Worker 后端

实施：

1. 比较当前基线与上游 2.44.9，先同步影响 API/格式转换的改动，记录固定提交；所有转换基准重新确认输出。
2. 从 `bench/` 提取生产入口和平台适配器，生产代码完全不包含测量路由、固定测试路径、模拟网络或 console 覆盖。
3. 明确平台环境标识，避免因为模拟 Surge/Node 环境而让用户脚本选择错误分支。
   已发现的具体问题：`utils/download.js` 的非 Node `tasks` Map 会在 DO 存活期间跨请求保留结果，并在 TTL/强制刷新判断前命中。原型已改为请求作用域，并用实际网络调用计数验证冷、热缓存，生产适配必须保留这项修正。
4. 保留同步存储契约与隐式变更追踪，管理写入和 Alarm 统一排队；schema 迁移只增不删，先保留可回退备份。
5. 首版保持官方前端的后端秘密前缀协议，以高熵 Worker Secret 配置；管理接口不缓存、不记录完整秘密路径。下载/分享保留原版 token 校验。若换为 Bearer 或登录会话，必须同时适配前端，不能仅改后端。

验收：API 创建、编辑、删除、预览、下载、导入恢复；并发修改；DO 驱逐/重启后恢复；无正确管理凭据不能访问管理数据。通过后才生成正式 Wrangler 部署配置。

## 阶段 2：脚本兼容层

实施：

1. 把实验 HTTP bridge 变为稳定的 `$substore.http` 接口，支持原版常用返回结构、二进制模式、超时和错误。
2. 在请求级 `RequestBudget` 中统一计算所有 HTTP/DoH 请求、重定向和重试，40 次业务预算，默认并发 4。
3. 中断预算独立于时钟；补齐跨异步段、嵌套 VM 的共享预算，以及资源释放。
   脚本结束时取消未完成宿主 I/O，禁止迟到回调操作已释放 VM。
4. 让脚本执行错误通过显式结果契约进入 API；默认禁止失败后伪装成处理成功，兼容“忽略失败”必须是明确选项。
   区分上游入口探测/函数名回退和实际执行异常，避免把合法回退标记为失败。
5. 针对对象原地修改、Promise、同步 lodash 回调、Buffer、正则、缓存与嵌套产物建立契约样本。不宣称任意 Node 模块兼容。

验收：999 节点纯计算脚本；单次及并发 HTTP；超预算失败；两个时钟冻结下的无限循环；内存上限；异常后的下一请求仍正常。使用用户真实脚本补最后一轮回归。

## 阶段 3：解析缓存与输出缓存

实施：

1. 来源内容摘要未变时复用归一化节点，绕过重复 YAML AST 构造。
2. 缓存 key 包含 revision、输入/脚本摘要、目标和影响输出的参数。
3. `live` 保持原版执行时机；`snapshot` 显式选择定时产出。含副作用的脚本不能自动改成缓存输出。
4. 原子切换完整产物；旧任务不能覆盖较新的 revision；配置编辑、删除、重命名和恢复都使相关缓存失效。
5. 限制内存缓存总字节数和单值大小。下载直接读产物时不重新解析节点。

验收：不同输出参数不会串缓存；失效后生成新版本；失败不覆盖已有有效产物；并发更新期间不发布旧 revision；999 节点反复下载的本地堆趋势稳定。

## 阶段 4：持久调度与外部功能

实施：

1. 将已验证的批次游标逻辑合并进业务 DO 的任务表与 Alarm。
2. 实现原版定时表达式/时区转换、任务状态、去重、退避与重启恢复。DO 单 Alarm 每次调度最早任务。
3. 节点信息先去重和查缓存，40 条/批、并发 4；完成后再运行依赖这些结果的脚本。
4. 接入 Artifact 定时生成、Gist 备份/同步与 HTTP 推送；通知类非幂等外部接口明确重复投递边界。
5. MMDB/R2、TCP/TLS DNS 作为独立可选能力，未完成前返回具体的不支持原因。

验收：中间批次重启、模拟失败和重复触发；999 查询只产生 999 个结果；缓存命中不发 HTTP；过期后重新查询；调度器空闲时不依赖持续计时器保活。

## 阶段 5：云端 Free 账号验收

此阶段需要明确的部署授权和目标 Cloudflare 账号，当前没有执行。

- 采集入口 Worker 与 DO 的真实 CPU、内存、请求/Alarm 次数、SQL 行读写和 duration。
- 使用 999 节点验证一次冷启动、连续转换、缓存命中及实际 HTTP 失败恢复。
- 重点观察 YAML 与脚本组合的 isolate 峰值内存。本地 GC 后的小堆不能作为云端峰值安全证明。
- 检查真实源站是否接受 Cloudflare 出口，以及第三方查询服务自己的频控和授权。
- 至少覆盖一个完整调度周期及一次 DO 驱逐恢复；通过后才将状态改为生产可用。

## 最小发布范围

完成阶段 1～3 后，可发布“本地验证版”，明确网络密集任务和定时功能的状态；完成阶段 4～5 才能宣称目标工作流在 Workers Free 上验收通过。当前仓库保持研究/原型状态，不以部分本地测试代替完整兼容声明。
